# Hermite Site — Project Plan

Hermite's own product website: marketing/landing, the full four-stage feature roadmap (Motion, Subs, AI, Enterprise API), and `/docs` for the enterprise API + MCP/Composio integration. No separate showcase brand. Companion to [HERMITE-PLAN.md](./HERMITE-PLAN.md).

## 0. Where it lives — same repo, decided

The site lives in **`/site` inside this monorepo** (not a linked repo). This is already the committed layout, and it's the right call because the progress-sync story collapses to almost nothing: the roadmap/status data lives at the repo root, the site imports it, and every push to the production branch redeploys the site through Vercel's git integration. One PR can change plugin code *and* flip a roadmap item to "shipped" atomically.

- **Vercel project:** framework preset **Next.js**, **Root Directory `site`**, build/output on auto-detect.
- Set an **Ignored Build Step** so site deploys skip when `site/` (which contains `site/data/`) didn't change: `git diff --quiet HEAD^ HEAD -- site`.
- Production branch: currently the working branch is the repo default; once work merges to `main`, point Vercel's production branch at `main`.

## 1. Site structure

All feature pages show the **full roadmap** — everything planned, not just what's built — with per-item status badges (`shipped` / `in-progress` / `planned`) driven by `data/roadmap.json`, never hand-edited copy.

- `/` — landing. Clay-directed hero, one-paragraph pitch, the four pillars as cards linking to their pages, a **build-in-progress strip** (current stage + latest changelog entries + link to GitHub), waitlist capture, footer.
- `/motion` — animation/easing/speed-ramp toolkit (Stage 1). Preset gallery, curve-editor story, `.drfx` install explainer.
- `/subs` — on-device auto-subs (Stage 2). The privacy pitch lives here: "your audio never leaves your machine," model choices, correction-pass workflow.
- `/ai` — local AI model picker (Stage 3). Model manager, RAM/disk guidance, the punctuation-cleanup first use case; clear disclosure of the optional OpenRouter cloud tier as opt-in.
- `/enterprise` — the Stage 4 API as a **visibly separate product line**: cloud by design, for customers who want that. Plans, MCP/agents positioning, link into `/docs`.
- `/roadmap` — the four stages laid out in full with statuses + the changelog feed (from `data/changelog.json`).
- `/pricing` — consumer desktop license and enterprise API plans side by side, both checking out through Polar. Ships as "join the waitlist" until Stage 1b is sellable.
- `/docs` — the technical docs section (see §3): API reference (endpoints, auth, rate limits, example requests/responses) and the MCP/Composio setup guide (connect Hermite as a tool for Cursor or a custom agent). Versioned, code-sample-heavy, its own content type and layout — not a marketing page.

## 2. Progress-sync mechanism

Options considered:

| Option | How | Needs | Verdict |
|---|---|---|---|
| **A. GitHub Action regenerates changelog** on push/release from commits/PRs/CHANGELOG.md, then redeploys | CI workflow + commit back or build-time fetch | Actions workflow; `GITHUB_TOKEN` (automatic, same repo — no secrets) | Right for the **changelog** only, triggered on **releases** so entries are curated, not raw commit noise |
| **B. Webhook endpoint** receiving push/release events, writing to a DB/CMS the site reads | Serverless route + datastore + webhook secret | Hosting for endpoint, DB, secret management | Overkill — real infrastructure to babysit for data that changes a few times a week |
| **C. Hand-maintained `roadmap.json`** in the repo, copied into the site's data folder on push | A file + (in a split-repo world) a copy Action | Nothing | Right for the **roadmap** — status flips are deliberate editorial decisions, and a human editing one JSON field is the honest workflow |

**Recommendation: C for roadmap + A for changelog — and because the site shares the repo, both get simpler than stated.**

- `site/data/roadmap.json` — single source of truth: stages → features → `{ id, title, blurb, status }`. The site statically imports it; editing a status and pushing *is* the sync (Vercel redeploys automatically; no copy step, no webhook, no secrets).
- `site/data/changelog.json` — regenerated by a small GitHub Action on **release published** (from the release's tag, name, and notes), committed back to the repo, which triggers the site redeploy. Uses the automatic `GITHUB_TOKEN`; zero external secrets. Until releases exist, seed it by hand in the same shape.
- The landing strip and `/roadmap` read only these two files, so site copy never needs rewriting to reflect progress.

## 3. Tech stack

- **Next.js (App Router) + TypeScript** in `/site` — matches the Vercel project already created, the ecosystem of the other two sites, and the serverless needs below. MDX enabled for long-form content.
- **`/docs` in the same app via Fumadocs**, not a subdomain. Fumadocs is a Next.js-native docs framework that provides exactly what the marketing template shouldn't be bent into: sidebar nav, doc search, versioned content, first-class code blocks with tabs, and OpenAPI-driven API reference generation (later, `/api` can export an OpenAPI spec that the reference pages render from — no hand-duplicated endpoint docs). Resolution of the layout-consistency tension: `/docs` lives in its own route group with the Fumadocs layout but inherits Clay's **tokens** (type, color, spacing) so it reads as the same brand, while marketing pages keep the full art-directed Clay treatment. One deploy, one domain, shared analytics — a subdomain buys nothing here but a second pipeline.
- **Clay design system via getdesign**: run `npx getdesign@latest add clay` at the project root, read the generated `DESIGN.md`, and follow it for all marketing UI rather than inventing a style. The current placeholder page in `site/` is explicitly throwaway and gets replaced by this pass.

## 4. Tooling integration

- **PostHog** — the primary analytics surface (unlike the plugin, where it's strictly opt-in; a marketing site is expected to measure itself — still use a proper consent banner and respect DNT). Funnels: landing → feature page → waitlist signup; landing → pricing → Polar checkout click; `/enterprise` → `/docs` → API-plan click.
- **Sentry** — Next.js SDK, one project covering client, server components, and route handlers (the plugin's backend/app split into separate projects doesn't apply here; client/server are distinguished within the project).
- **Polar.sh** — checkout/billing surface: consumer desktop license and enterprise API plans as **two separate Polar products/pricing tables**, surfaced on `/pricing`. Webhook route handler (`/api/webhooks/polar` inside the site app) verifies signatures and triggers Resend receipts.
- **Resend** — waitlist confirmation (double opt-in), purchase receipts (from Polar webhooks), and changelog/update broadcast emails to the waitlist on each release.
- **Jest** (+ React Testing Library) — applies cleanly here since the site is fully JS/TS: component tests for roadmap/status rendering (a `roadmap.json` fixture with each status renders the right badge), unit tests for the changelog transform, handler tests for the waitlist and Polar webhook routes (signature verification included).
- **OpenRouter** — **skipped for v1.** It belongs only if an interactive AI demo widget (e.g. "try the caption cleanup") ships; that's a post-launch experiment, and when it happens it must be clearly labeled as a network call.

## 5. Build plan — milestones

1. **Scaffold + Clay**: upgrade the placeholder `site/` app (MDX, route groups), run `npx getdesign@latest add clay`, read `DESIGN.md`, establish tokens/fonts/layout primitives from it.
2. **Landing page** per Clay: hero, pillar cards, waitlist form (UI only), footer.
3. **Roadmap data layer**: `data/roadmap.json` schema + seeded content from HERMITE-PLAN.md; `/roadmap` page; status badges; build-in-progress strip on the landing page; hand-seeded `data/changelog.json`.
4. **Feature pages**: `/motion`, `/subs`, `/ai`, `/enterprise`, each rendering its roadmap slice; the on-device privacy story on `/subs`–`/ai`, and the explicitly-cloud positioning on `/enterprise`.
5. **`/docs` via Fumadocs**: docs shell + MCP/Composio setup guide (writable now); API reference structure with endpoints marked **Draft — API in development** until Stage 4's `/api` exists, then regenerated from its OpenAPI spec.
6. **Wiring**: Resend waitlist (double opt-in), PostHog + funnels + consent, Sentry.
7. **Commerce**: `/pricing` with Polar checkout for both product lines + webhook → Resend receipts (behind "coming soon" until there's something sellable).
8. **Automation + hardening**: release-triggered changelog Action, Vercel ignored-build-step, Jest suite, deploy to production domain.

Dependency note: milestones 1–6 need nothing from the plugin's Stages 2–4; only the *final* API reference content depends on `/api` existing. The site can and should ship the vision well before the product is finished — that is its job.
